# 5 消息渠道

规则修订、赛程调整与报名审查通知分散在多个官方渠道。之所以必须建立常态化的信息跟踪机制，是因为 RoboCup HSL 是一项规则动态演进的高技术联赛，任何关键规则的调整（如传感器禁令收紧、草皮高度改变或点球规则修订）都会直接撼动算法假设；如果未能及时感知，往往导致投入大量精力的研发方案在赛前检录中直接被判定违规。

## 5.1 优先关注的两个核心渠道

1. **官方邮件列表（Mailing List）**  
   技术委员会（TC）与执行委员会（EC）通常通过邮件列表发布规则修订征集、报名资格审查通知与技术决议。
   - 订阅地址：[robocup-humanoid 邮件列表](https://lists.robocup.org/mm/lists/robocup-humanoid.lists.robocup.org/)
   - 之所以必须使用队内公共邮箱统一订阅，是因为高校战队成员面临毕业离队流动，如果使用私人邮箱订阅，极易在人员交接时造成信息断档，由此导致战队错过关键材料提交节点，直接丧失参赛资格。
2. **官方 Discord 核心社区**  
   技术委员会、裁判组与全球参赛队日常技术交流与答疑平台。现场比赛期间常用于发布临时网络调整与规则解释。
   - 加入链接：[RoboCup HSL Discord 邀请链接](https://discord.gg/67qGN8ycwz)
   - 规则文本通常高度凝练，关于特定边缘案例的裁量准则（例如机体倒地后与球门发生物理干涉的处理），通常在 Discord 历史讨论中有裁判长给出的明确答复。提问前应当检索历史记录，技术咨询时必须附带现场环境参数与日志。

## 5.3 代码与工具仓库

| 仓库名称 | 工程应用场景 |
| :--- | :--- |
| [HSL-Rules](https://github.com/RoboCup-HumanoidSoccerLeague/HSL-Rules) | 官方规则 LaTeX 源码与发布版 PDF；查阅条款修订历史与具体年份变更记录 |
| [GameController](https://github.com/RoboCup-HumanoidSoccerLeague/GameController) | 裁判盒官方软件源码与二进制运行包；本地联调与验证网络数据包字段结构 |
| [RobotInspection](https://github.com/RoboCup-HumanoidSoccerLeague/RobotInspection) | 机器人赛前检录规范与计算检查工具；提前核验身高、体重与足底面积参数 |

核对规则时，必须以官方 GitHub 仓库最新发布的 release 标签对应源码为准。之所以不能仅看本地流传的 PDF 文件，是因为官方常在赛前发布勘误补丁，若依据过时草案设计代码，现场测试极易陷入违规困境。

## 5.4 一个赛季的研发节奏

| 阶段划分 | 研发重点与任务目标 |
| :--- | :--- |
| **赛后复盘与冬训期** | 全面梳理当季比赛暴露的稳定性缺陷，确定新赛季系统架构重构目标，整理知识交接文档 |
| **年初准备期** | 紧密跟踪官方网站发布的报名通知与资格审查细则，组织团队撰写并完善 TDP 技术报告 |
| **春季资格审查期** | 录制并剪辑资格审查实机运行视频；按新赛季规则修订软件逻辑并完成全项目自检 |
| **赛前两个月集成期** | 全面启动整机系统联调，全流程模拟真实对抗场景；高频演练裁判盒通信与断网重连 |
| **比赛现场执行期** | 现场标定光照曝光与网络路由配置；每日赛后坚持复盘并记录实测参数改动 |

## 5.5 队内信息维护流程

为了防止关键技术信息被遗漏，战队应当落实明确的职责分配：
- 指定专人每周查阅官方邮件列表，一旦发现赛制或资格审核变动，立即组织研读并通报全队。
- 指定专人关注 Discord 中的 `#rules` 规则咨询频道与官方公告频道，追踪各队对新规则的技术争议。
- 对官方 `HSL-Rules` 仓库建立星标与更新提醒，一旦主分支发生合并或发布新 release，第一时间比对差异并评估对现有代码的影响。
- 每次赛季结束后，将当届比赛使用的规则 PDF 及其对应的 commit 哈希完整归档至队内知识库，使后续开发保持清晰的历史可溯性。
