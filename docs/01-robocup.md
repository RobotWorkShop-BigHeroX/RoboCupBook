# 1 RoboCup 与 HSL

RoboCup 于 1997 年举办首届赛事。其长期目标，是推动全自主机器人足球发展到能够与人类顶级球队竞技的水平。人形机器人足球（Humanoid Soccer League, HSL）是其中一条技术路线，要求机器人在完全脱离人工遥控的条件下，自主完成环境感知、战术决策和运动控制。

在这一竞技场景中，“全自主”要求机器人必须依据机载传感器独立作出对抗决策；“人形”则迫使机体必须在双足交替离地的非连续支撑状态下维持动态平衡。感知、决策与运动控制系统必须在极为有限的机载算力与严格的实时通信约束下高度协同。

## 1.1 机器人足球考验什么

机器人足球之所以对工程系统构成极其严苛的挑战，是因为它将视觉感知、状态估计、战术决策与运动控制紧密咬合在一个连续反馈的闭环回路之中。机器人必须持续从机载相机捕获的高清图像中检测球体与场地标线，借以推算机体在地图中的实时位置；随之根据当前的对抗态势与裁判盒指令选定动作目标；最终将目标速度解算为数十个电机的关节轨迹。

这一长链路的因果依赖，导致上游任何微小的时延抖动或观测误差都会在下游被级联放大。例如，由于图像传输或模型推理产生了 200 毫秒的时延，球体坐标解算便会落后于物理真实轨迹，此时运动控制器哪怕分毫不差地执行了踢球动作，实际上击打的也只是球体早先滚过的虚影，由此导致踢空甚至由于重心突变失衡摔倒。

团队通常沿着这条数据因果链划分研发职责：感知模块负责从原始像素中解算机器人、球体和场地的空间坐标；策略模块根据这些状态信息与裁判指令选定战术行为；运动控制模块则将目标行为转化为可执行的关节力矩与轨迹。上游输出的精度与延迟直接决定了下游执行的上限。

比赛规则对自主运行和外部通信施加了物理隔离层面的限制。这迫使软件架构必须将全部决策与推理逻辑部署在机载计算单元上，杜绝任何依赖场外服务器辅助计算的侥幸假设。

## 1.2 相关组别与技术积累

之所以要追踪 RoboCup 早期组别的技术演进，是因为人形机器人足球大量继承了标准平台组（SPL）与中型组（MSL）沉淀下来的技术资产。

| 组别 | 状态 | 留给 HSL 的资产 |
| :--- | :--- | :--- |
| **SPL 标准平台组** | 并入人形体系 | 提供了成熟的粒子滤波定位、多机网络通信与行为树战术架构。B-Human 团队的代码库是这一演进脉络的完整工程参照。 |
| **MSL 中型组** | 停办 | 沉淀了全向底盘轨迹规划与高速弹射击球算法。双足行走虽然无法直接借用其运动学，但其多机跑位几何建模依然具备参考价值。 |
| **仿真组** | 压缩规模 | 提供了低成本算法回归与策略预演环境。能够用于跑通通信链路与战术逻辑，但无法反映真机足底接触碰撞与电机热衰减。 |
| **@Home 服务组** | 独立发展 | 专注于家庭生活服务场景，与足球对抗无关。本书不涉及。 |

> 注：组别设置随技术委员会决策动态调整，具体以当届官方公告为准。

不同硬件形态之间的物理约束存在本质差异。轮式底盘具备连续稳定的平面支撑，因而可以专注于全局战术规划；人形双足机器人则迫使开发者必须将主要计算精力分配给维持动态平衡与处理足底非连续冲击。不利与风险往往潜藏于盲目的代码移植之中：步态与平衡算法与机体质量分布和关节减速比强绑定，无法直接套用；最有效的办法，是吸收其在状态机调度、裁判盒交互与网络容错方面的架构经验，将具体运动控制限制在适配本队机体动力学的范围内。

## 1.3 一场比赛的全过程

一场正式比赛不仅包含场上的动态对抗，还涵盖严格的赛前检录、多阶段状态流转以及赛后故障维护。软件必须针对每一个裁判状态设计受控的行为边界，尤其要使机器人在非对抗阶段保持绝对受控。

| 阶段 | 场上发生什么 | 程序的处理动作 |
| :--- | :--- | :--- |
| **赛前检录** | 裁判实测机体身高、称量全备重量、核验传感器合规性 | 提前测量几何尺寸与重量，为配重平衡调整预留缓冲时间 |
| **INITIAL** | 机器人在场外待命，等待入场指令 | 仅保持监听裁判盒广播，禁止输出底盘驱动力矩。所有电机处于安全零力矩或阻尼状态 |
| **READY** | 机器人自主走到开球站位 | 接收到开球信号后自主走位到达指定半场点位，同时利用视觉特征加速完成初始定位收敛 |
| **SET** | 全部机器人就位，进入静止确认期 | 冻结底盘速度并锁定关节，保持完全静止，准备执行开球程序 |
| **PLAYING** | 比赛计时开始，双方自由对抗 | 感知、决策与运动控制全频段运行，状态机依据战术目标持续分配移动与射门任务 |
| **半场** | 上下半场交换进攻场地 | 接收半场信号后执行全局坐标镜像旋转，重新初始化攻守朝向定位 |
| **FINISHED** | 终场哨响，全场比赛结束 | 立即切断运动规划并进入安全保护模式，等待随队人员入场关闭动力 |

在多机协作赛制下，机器人之间必须基于共享黑板协商站位与防守职责。之所以不应将场上人数硬编码在程序中，是因为一旦出现队员被红牌罚下或发生机械故障离场，动态阵型调整机制必须能够自适应切换为防守补位模式，否则将导致关键防区出现无人看管的致命空当。

## 1.4 场地条件对算法的影响

场地物理环境是算法执行的物理边界。实验室理想地面与赛场实际环境之间存在明显偏差，算法设计必须充分包容物理扰动：

| 场地元素 | 物理属性 | 对算法的影响 |
| :--- | :--- | :--- |
| **人工草皮** | 表面存在长年倒伏反光，纤维阻尼较大 | 强反光导致基于颜色阈值的球体分割失效；草皮摩擦阻尼不均迫使里程计产生非线性打滑，必须依赖视觉持续校准漂移 |
| **白色标线** | 边界线、中线、中圈与禁区几何线段 | 定位系统的绝对几何基准；线宽恒定，利用透视投影几何关系可逆向约束相机到标线的距离与夹角 |
| **中圈与罚球点** | 圆形轮廓与点状几何标记 | 场地中心两侧几何对称，一旦跌倒爬起后初始朝向偏差过大，极易引发半场认反并导致定位坐标颠倒 |
| **球门立柱** | 白色双立柱配合顶部横梁 | 射门瞄准的关键物理参照；立柱几何截面较细，远距离容易丢失，必须结合地图全局坐标进行位姿推算 |
| **黑白足球** | 标准白底黑斑多面体 | 快速滚动作态下产生严重的运动模糊，检测模型必须具备抗模糊特征提取能力 |
| **环境光照** | 场馆吊顶射灯与室外漫射光叠加 | 照度随场地区域与赛程时段发生剧烈漂移，迫使相机驱动必须具备曝光抑制与白平衡自适应能力 |

现场出现感知或定位故障时，应当沿着“环境光照变化 → 图像特征提取丢帧 → 粒子滤波发散 → 策略节点接收空数据”这条因果链逐步排查，避免在缺乏日志证据时盲目改动参数。

## 1.5 规则里和写代码有关的六条

HSL 赛事规则对机载系统设计施加了硬性约束，直接决定了软件实现的边界：

1. **全自主决策原则**：比赛期间严禁任何形式的外部遥控干预。全部运算必须在机载工控机内独立完成，通信仅限于接收裁判盒广播与队友协同消息。
2. **尺寸与全备重量上限**：机械结构改动必须严格受限于规则规定的高度与质量包络。检录一旦超标将直接丧失参赛资格，因此硬件增重会迫使算法层压缩算力冗余以适配紧凑硬件。
3. **传感器选型限制**：赛事严禁使用任何激光雷达或外部辅助定位发射器；深度相机在室外光照下容易出现大面积点云噪点且受到检录严密审查。这迫使系统必须依靠单目/双目可见光相机配合足式里程计完成全自主导航。
4. **换人与离场惩罚代价**：机器人被罚下或申请维修必须等待死球时间，重新入场必须在场边接受罚时计时。策略层必须具备处理减员局面的阵型自适应能力。
5. **身体对抗与危险动作判定**：高动态推挤、恶意铲球或守门员超时持球均会招致黄牌判罚。策略层在设计逼抢动作时，必须为减速制动保留物理缓冲距离。
6. **半场攻守换边机制**：上下半场双方互换场地。这迫使底层定位系统与顶层射门决策禁止将坐标常量写为固定正负值，必须通过全局坐标变换矩阵实现一键镜像。

## 1.6 裁判盒：机器人听谁的话

GameController（比赛控制程序，简称裁判盒或 GC）是球场上的最高裁决信号源。机载系统通过监听其网络广播决定程序执行状态。

- **工作机制**：主裁判在现场控制台操作 GC 软件，切换赛事阶段；GC 通过场地局域网将结构化状态数据包持续广播至 UDP 3838 端口；场上各台机器人机载节点监听该端口并反序列化数据。
- **职责边界**：裁判盒不参与任何球体追踪或机体位姿解算。它只负责维护时钟计时、计分比分、广播比赛状态与记录罚时。机器人的自主定位与足球攻防完全由本机算法独立完成。
- **失步风险**：倘若机器人因网络拥塞或解析异常导致漏收状态包，将在暂停期继续违规走动并招致直接罚下。因此网络监听线程必须保持高优先级独立运行。

| 数据包核心字段 | 用途与工程意义 |
| :--- | :--- |
| **队伍编号（Team Number）、球员编号（Player ID）** | 判定当前广播包是否属于本机；编号配置错误会导致所有状态指令被作为外部杂波丢弃 |
| **比赛状态（Game State）** | INITIAL / READY / SET / PLAYING / FINISHED，直接驱动底盘与行为树状态机切换 |
| **半场剩余时间（Estimated Secs）** | 驱动策略层评估进攻紧迫度，决定执行稳健控球还是全力压上远射 |
| **罚时计时（Penalty Status & Time）** | 提供场上减员状态与剩余解禁秒数，促使阵型动态收缩防线 |

首次现场联调应当按序执行验证：
1. 下载并运行与当届规则版本匹配的 GameController 程序。
2. 严格核对配置参数中的 Team Number 与 Player ID，使之与机载代码配置文件完全一致。
3. 将调试笔记本与机器人置于同一物理局域网网段，关闭操作系统防火墙干扰。
4. 使用抓包工具验证 UDP 3838 端口广播包接收正常，字段解析无乱码。
5. 执行完整的状态切换测试，观察机器人底盘是否严格遵循“INITIAL 静止 → READY 走位 → SET 锁定 → PLAYING 进攻”的生命周期。

联调阶段常见的失灵现象包括：队号配置错误导致广播包被忽略；系统多网卡路由冲突阻断了广播监听；或者换边逻辑未处理坐标镜像导致开球向本方大门冲刺。

## 1.7 五个常见误解

- **“机器人是遥控的吧？”**  
  HSL 联赛要求完全自主运行。场边安全员手持手柄仅用于在机体面临毁损风险时切入阻尼或安全停机，严禁输入任何移动或射门控制指令。
- **“必须购买官方指定整机？”**  
  规则仅对物理尺寸、重量和传感器类型设定准入包络。各支队伍不论采用商用采购平台还是自主研发机械本体，只要通过检录审查即可参赛。
- **“仿真环境跑通了，真机自然能行。”**  
  仿真引擎无法完全还原人工草皮的不规则顺逆纹理阻尼、电机发热导致的减速比转矩波动以及结构件微小旷量。真机调校必须建立在充分的实机测试与离线日志排查基础之上。
- **“规则是裁判的事，跟写代码关系不大。”**  
  赛事实体规则直接约束了传感器的选用边界、半场攻守镜像的坐标变换规范以及危险推挤的减速缓冲逻辑，直接决定了软件架构的核心输入。
- **“算法设计越复杂越先进。”**  
  在强动态物理对抗场景下，过度的算法复杂度会加剧机载计算负荷并引入难以复现的死锁隐患。模块边界清晰、因果推导可靠、故障排查便捷的稳健系统，才具备现场实战的可维护性。
