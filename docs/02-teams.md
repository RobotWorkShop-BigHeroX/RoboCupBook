# 2 强队与开源资产

开源代码和技术报告可以帮助新成员了解成熟系统的组织方式，也能提供可供验证的实现参考。不同赛季、规则和硬件之间存在差异，阅读时需要判断哪些设计可以复用。

下表列出值得研究的队伍，以及各自可以提供的参考方向。队伍战绩、技术报告和仓库状态应以官方资料为准。

## 2.2 B-Human：从它的文档入手

B-Human 团队会在赛后公开代码和技术报告。项目规模较大，初次阅读时不宜在目录中随机浏览文件；先了解系统的功能分层，再沿着一条数据流追踪实现，通常更容易建立整体认识。

| 层次 | 负责内容与阅读关注点 |
| :--- | :--- |
| **感知（Perception）** | 从图像中提取特征：球、线、球门柱、其他机器人。关注如何将一帧图像转化为结构化的观测。 |
| **建模（Modeling）** | 将观测转化为状态：球的位置和速度、自身位姿、对手分布。关注其状态滤波器的实现。 |
| **行为（Behavior）** | 决定执行动作：走位、抢球、传球、防守。关注其层次状态机的组织形式。 |
| **运动（Motion）** | 将目标动作转化为关节轨迹：步态、踢球、起身。关注参数的配置与暴露方式。 |
| **硬件（Hardware）** | 与电机、IMU 进行底层通信。通常无需修改，但需要理解接口协议。 |

### 建议的阅读顺序

1. 先读当年的技术报告，将五层架构的关系绘制为流程图。
2. 阅读核心数据结构定义。明确其如何表示球体位置与机体位姿，这决定了后续模块的输入输出接口。
3. 寻找数据入口：图像输入后的第一个处理函数位置；决策周期开始时的调用起点。
4. 选取一个独立模块深入阅读，例如只追踪球检测链路，贯通从图像输入到观测输出的完整过程。

### 值得关注的三个工程设计

- **黑板式数据流**：各模块将计算结果写入共享结构，其他模块按需读取，模块之间避免直接相互调用。新增模块时无需改动整条调用链路。
- **统一坐标约定**：全系统遵循一致定义的机器人坐标系，所有模块共同使用，防止各模块分散转换导致坐标不匹配。
- **参数外置管理**：阈值、速度与角度等参数统一放入外部配置文件，现场可直接调整，无需重新编译程序。

## 2.3 其他队伍的参考方向

- **Rhoban**：踢球动作采用参数化曲线组织。研究其实现时，关注动作参数如何暴露给调试人员，以及参数变化如何影响动作轨迹。
- **NimbRo**：自研硬件与整机系统具有参考价值，尤其是机械结构、散热设计、内部走线与全身动力学之间的协调关系。
- **Hephaestus 与 Mountain Sea**：可重点查阅其公开的定位、感知与步态资料，结合本队使用的硬件平台与场地条件评估适用性。

## 2.4 如何阅读陌生代码仓库

1. **先看文档和架构图**：通过 README、技术报告和模块架构图了解项目目标、依赖环境与整体结构，再进入具体代码实现。
2. **定位数据入口**：确认图像、裁判盒状态和运行日志分别从哪里进入系统。入口明确后，再沿着数据流定位负责处理的模块。
3. **追踪一条完整功能链**：例如从图像中的球检测开始，逐步追踪定位、目标选择、接近球体与踢球动作分别由哪些模块完成。
4. **进行小范围验证**：调整单个参数，在相同测试条件下重新运行并比对结果，确认对相关模块行为的理解。

阅读代码需要通过运行结果进行验证。调整参数后应记录修改前后的现象，避免将推测当作确认的结论。

## 2.5 TDP 怎么读

TDP（Team Description Paper，队伍技术说明文档）梳理各队当年系统设计、实现方案和实验结果，可从官方队伍名单页面获取。它面向技术评审，不一定包含全部实现细节，适合用于了解整体方案，再与代码、视频和历年版本对照。

阅读时优先核对三项内容：

1. **传感器配置与采样频率**：这决定了方案对机载算力的要求，也决定了方案是否能够在本队平台上复现。
2. **报告中指出的瓶颈**：注意报告是否说明了系统局限，例如远距离检测稳定性、定位对称结构歧义等。明确的局限有助于理解方案的适用边界。
3. **当年新增与调整的内容**：与上一年报告进行比对，可以看出团队重点投入研发的模块，以及改动是否带来了量化性能提升。

技术报告呈现的是队伍选择记录和展示的内容。对于关键设计与性能结论，应进一步查看具体实现、测试条件与对应版本。
