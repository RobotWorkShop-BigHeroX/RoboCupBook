# 2 强队与开源资产

开源代码与技术报告能够为新成员呈现成熟系统的实际组织方式。然而，各个赛季的规则演变、各支队伍采用的机械平台与传感器配置不尽相同，这迫使我们在阅读开源资产时，不能盲目照搬现成算法，而必须深入分析其背后的物理约束与设计初衷。之所以要研究强队的架构，是因为它们的代码结构经历过高强度对抗的反复检验，其工程取舍往往直接映射了人形机器人在高动态场景下所面临的核心矛盾。

下表列出八支值得深入研究的代表性队伍及其参考价值。队伍历史战绩与仓库地址以官方竞赛委员会发布为准。

## 2.2 B-Human 开源代码与技术文档

B-Human 团队每年赛后都会将整套比赛系统开源并发布长达数百页的技术报告。其项目规模十分庞大，初次阅读如果漫无目的地逐行浏览代码，极易陷入底层细节泥潭。最有效的办法，是先建立对系统分层架构的全局认知，随后沿着单一数据流进行定向追踪。

| 系统层次 | 职责划分 | 源码阅读核心关注点 |
| :--- | :--- | :--- |
| **感知层（Perception）** | 从原始相机图像中提取球体轮廓、场地白线、球门立柱与其他机体边界框 | 关注其如何利用快速图像扫描线算法与轻量神经网络，将每秒数十帧的原始像素压缩为紧凑的几何观测特征。 |
| **建模层（Modeling）** | 融合观测数据与时序先验，解算球体运动速度、机体自身坐标以及对手位置分布 | 关注其状态滤波器的具体实现，特别是运动预测与视觉更新如何协同抑制累计漂移。 |
| **行为层（Behavior）** | 依据场地全局状态与比赛阶段指令，仲裁机器人的战术意图与动作分配 | 关注其层次状态机或行为树的拓扑组织形式，以及攻防角色之间的动态协同机制。 |
| **运动层（Motion）** | 将高层决策下发的期望速度或踢球指令，转化为十二个下肢关节的力矩与角度轨迹 | 关注关键动作曲线的参数暴露方式，以及摆动相与支撑相的相位切换条件。 |
| **硬件层（Hardware）** | 负责机载工控机与电机伺服驱动器、IMU 姿态传感器之间的底层通信总线交互 | 理解其底层通信协议与报文收发时序，重点关注通信掉包与超时保护机制。 |

### 建议的代码阅读路径

1. **研读当年技术报告**：先阅读技术报告中的总体架构章节，将五层架构之间的数据传递关系手绘为时序调用流程图。
2. **核对核心数据结构**：深入阅读基础通信数据包定义。明确球体位置与机体位姿在内存中如何表示，因为数据类型的定义直接规定了所有模块的输入输出契约。
3. **定位系统调用入口**：寻找主循环的滴答触发源，明确单帧图像输入系统后的首个解析函数位置，以及每个决策周期触发的顶层入口。
4. **单线贯穿追踪验证**：选取一条独立功能链路进行纵向深挖，例如只追踪“足球识别与追踪”这一条线，完整贯通从图像像素输入到观测特征输出的全过程。

### 值得深入借鉴的三个工程设计

- **黑板架构数据流**：各功能模块仅将计算产物写入全局共享黑板，其他模块按需拉取数据，模块之间严格禁止发生直接耦合调用。之所以采用黑板模式，是因为当战队需要新增传感器或重构算法时，无需改动现有的整条调用链，大幅降低了系统维护风险。
- **全局统一坐标约定**：全系统必须严格遵循统一规定的机体与场地坐标系，所有感知检测与运动控制模块均在此坐标系下进行运算。之所以强调全局统一，是因为如果各个模块各自私下进行坐标旋转与单位换算，微小的时间戳不同步与角度偏差将直接导致落脚点解算完全偏离，最终引发空踢或失衡摔倒。
- **参数外置与热重载**：系统运行涉及的所有置信度阈值、行走步频步长与安全限位角度，统一保存在外部配置文件中。之所以采取参数外置，是因为比赛现场的草皮阻尼、环境光照与电池电量均具有不确定性，迫使战队必须具备就地快速微调的能力；若将参数硬编码在源码之中，每次改动均需重新编译，在紧张的赛前准备与局间暂停期将承受极高的操作风险与时间成本。

## 2.3 其他队伍的参考方向

- **Rhoban**：踢球动作完全采用参数化多项式曲线生成。研究其开源代码时，重点分析动作参数如何暴露给调试人员，以及参数微调如何改变末端脚掌的空间运动轨迹。
- **NimbRo**：自研整机与高动态硬件具备极高的参考价值。之所以要研究其机械结构与机电布局，是因为机器人在高动态对抗中不仅需要聪明的算法，更依赖可靠的机械刚度、充裕的散热风道以及规整的内部走线。
- **Hephaestus 与 Mountain Sea**：重点查阅其发表的学术论文与开源算法包，结合国内统一硬件平台的计算特性与场地实测条件，评估相关定位与步态补偿算法在自身平台上的迁移可行性。

## 2.4 如何高效阅读陌生代码仓库

面对十万行量级的陌生机器人工程代码，必须遵循工程化的逆向阅读方法：

1. **从文档与拓扑图切入**：通过 README、技术报告以及官方架构图，弄清该项目的软硬件依赖关系、编译系统以及核心功能切分，避免过早陷入代码细节。
2. **定位硬件与网络入口**：明确相机视频流、IMU 姿态数据、裁判盒广播数据分别通过哪一个节点或函数注入机载系统，入口明确后才能顺流而下进行逻辑追踪。
3. **单条功能闭环贯通**：挑选业务逻辑最清晰的完整链路进行研读，例如从“相机检测到足球”开始，逐步追踪“定位解算相对坐标”、“行为树选定接近球动作”、“步态规划器输出行进步长”直到“驱动器下发执行指令”。
4. **单变量参数扰动验证**：在仿真环境或安全保护吊绳下，故意修改单一参数（如调小识别置信度阈值或调整摆腿抬高量），对比修改前后的物理表现，借以验证自身对该模块运作机理的理解是否准确。

阅读代码必须紧密结合运行验证。任何没有经过真实执行与现象记录的逻辑推论，都只能作为待证假设，绝不能草率当作已确认的工程事实。

## 2.5 队伍技术报告（TDP）的研读要点

TDP（Team Description Paper，队伍技术说明文档）是各参赛队伍提交给技术委员会的正式资格审查报告，浓缩了该队当年的系统设计亮点、硬件方案与实测数据。研读 TDP 时，应当重点聚焦以下三个核心问题：

1. **传感器配置与计算调度频率**：明确对方采用了何种型号的工控机、相机与 IMU，以及各核心算法节点的实际运行频率。这决定了该技术方案对物理算力的底线要求，也是评估本队平台能否复用该方案的前提条件。
2. **瓶颈记录与适用局限**：成熟队伍通常会在报告末尾坦诚分析系统现存的短板，例如远距离标线特征稀疏导致定位漂移、强逆光环境下球体误检率上升等。这些局限说明了特定算法的物理失效边界，能帮助我们在技术选型时规避弯路。
3. **历年增量对比**：将该队当年的 TDP 与上一年的报告进行横向对比，重点分析其在哪些模块上进行了重构，以及这种改动是否带来了赛场比分或运行稳定性上的量化提升，由此推断出当前技术演进的真正突破点。
