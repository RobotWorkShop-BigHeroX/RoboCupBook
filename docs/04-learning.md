> 不要只依赖 AI 生成代码而不理解其行为；同样，也没有必要逐行读完所有依赖。更有效的起点，是先跑通一条完整功能链，再围绕遇到的问题阅读代码。  
> 禁止完全许愿式编程，但也不必转向一行行了解代码，这就像从一个低效走向另一个低效。  
> —— andinm_hong

## 4.1 可以暂缓学习的内容

初期可以先放缓对以下内容的深入学习：

- **DDS 底层协议细节**：初期理解节点自动发现与主题发布订阅机制即可，遇到偶发掉线再深入分析传输协议层。
- **Executor 执行器底层源码**：先掌握单线程与多线程执行器的调度差异，明确耗时回调对实时调度的影响。
- **C++ 高级模板元编程**：现役代码中部分底层库包含模板，如果不直接修改基础库实现，不影响业务代码开发。
- **强化学习数学证明**：初期注重训练环境搭建、动作空间定义、评估指标与收敛曲线分析，理论证明可根据项目需要逐步补充。
- **排版工具格式细节**：无需关注 LaTeX 宏包与排版语法，重点在工程逻辑与算法实现。

## 4.2 Git：建立基本协作习惯

| 日常任务 | 对应命令 |
| :--- | :--- |
| 查看本地改动状态 | `git status`、`git diff` |
| 交互式分块暂存提交 | `git add -p`（逐块核对代码改动） |

| 同步远程分支最新提交 | `git pull --rebase` |
| 创建并切换开发分支 | `git switch -c feat/ball-tracking` |

### 协作约定

1. **禁止对公共主分支执行强制推送（force push）**：这会覆盖其他成员的工作成果并破坏协作历史。
2. **每次提交保持职责单一**：避免将功能修复与大规模代码格式化混杂在同一提交中，以便审查与必要时的追溯。
3. **提交 PR 前在本地完成测试验证**：自动化持续集成流水线用于把关，不能取代开发者本地的基础验证。

## 4.3 ROS 2 的常用机制与适用场景

| 核心机制 | 解决的工程问题 | 常见调试场景 |
| :--- | :--- | :--- |
| **DDS / RTPS** | 去中心化节点自动发现与高吞吐传输 | 局域网内机器重启后的节点重连排查 |
| **节点与通信模型** | 模块解耦，通过话题、服务与动作进行交互 | 梳理系统架构与数据调用关系 |
| **QoS 服务质量策略** | 规定消息可靠性、队列缓冲深度与保活要求 | 解决画面延迟过高或比赛状态偶发丢包 |
| **Executor 执行器** | 调度回调函数并发线程与优先级 | 解决控制周期抖动与多回调死锁问题 |
| **Lifecycle 生命周期** | 提供明确的节点状态机（未配置/激活/失活） | 比赛上场前顺序自检与停机安全保护 |
| **Node Composition** | 支持多节点在同一进程中运行，实现零拷贝通信 | 解决高分辨率高帧率图像在进程间拷贝占用过高问题 |
| **TF2 坐标变换系统** | 维护机器人机体、传感器与球场的空间树形转换 | 将图像中识别到的目标映射为球场绝对坐标 |
| **rosbag2 数据录制与回放** | 完整记录现场传感器与话题通信时序数据 | 赛后离线回放现场数据复现偶发故障 |

### QoS 配置对图像延迟的影响

例如：若相机话题配置为 `RELIABLE`（可靠传输）且队列深度设为 10，当检测节点的处理帧率低于相机采集帧率时，历史数据包将在队列中积压。运动控制节点读取到的视觉结果将存在时间差，导致机器人朝旧位置移动。

对于强调低时延的高频传感器（相机与 IMU），通常采用 `BEST_EFFORT`（尽力传输）并将队列深度设为 1，舍弃旧数据以获取最新状态；而裁判盒状态则需要选用 `RELIABLE` 策略以避免关键指令丢失。

### 基本坐标变换链路

相机捕获的球体坐标最初位于相机光学坐标系；若要在球场中规划逼近路径，必须依次执行以下空间坐标转换：

$$\text{相机坐标系 (camera)} \xrightarrow{\text{URDF 结构}} \text{机体基坐标系 (base)} \xrightarrow{\text{足式里程计}} \text{里程计坐标系 (odom)} \xrightarrow{\text{全局定位}} \text{球场地图坐标系 (map)}$$

### 端到端数据链路时延测量

真实链路运转示例：
相机采集图像（30 Hz）→ 图像预处理与检测（TensorRT 推理）→ 输出目标球体空间坐标 → 定位节点结合里程计更新全局位姿 → 决策节点计算期望速度（10 Hz）→ 运动控制输出关节指令（200 Hz）。

链路中各环节均会产生传输与计算耗时。当发现机器人反应迟钝时，应使用时间戳对各阶段耗时进行测量，定位性能瓶颈后再执行优化。

## 4.5 视觉检测流程与检查项

| 开发阶段 | 交付目标 | 验收指标 |
| :--- | :--- | :--- |
| **数据采集** | 比赛现场光照条件下的真实图像 | 覆盖日照、室内灯光与逆光等多种光照条件 |
| **样本标注** | 足球、立柱、球门线与各色机器人 | 标注边界准确，不同人员标注保持一致 |
| **模型训练** | 满足收敛要求的权重文件 | 验证集指标稳定，损失函数曲线平缓收敛 |
| **模型导出** | 编译为 TensorRT 引擎文件（`.engine`） | 精度损失可控，推理时延在毫秒级预算内 |
| **机载部署** | 接入 ROS 2 节点并在硬件上运行 | 连续长时间运行无显存泄漏或异常挂起 |

### 常见视觉问题与应对策略

| 异常表现 | 可能原因与对策 |
| :--- | :--- |
| **画面过曝** | 强光下草皮与白线反光发白。设置自动曝光上限，或针对场地执行手动标定。 |
| **运动模糊** | 快速转身时目标产生拖影。提高相机快门速度，平衡感光噪点。 |
| **类别不平衡** | 球体样本充足但立柱与特定色块样本匮乏。按类别调整损失权重或针对性补充数据。 |
| **域偏移现象** | 模型在实验室运行良好，但在比赛场地漏检增多。检查训练集是否覆盖现场特定光照与背景。 |
| **推理时延过高** | 检测精度达标但计算帧率不足。检查图像尺寸预处理是否使用 GPU 加速，核查 TensorRT 量化配置。 |

现役方案以 YOLO11 配合 TensorRT 为基准，YOLO26 可用于平行对比实验。未经受控对比测试前，赛前避免更换基础检测模型。

## 4.6 行为树与状态机的分工

| 维度 | 有限状态机（FSM） | 行为树（Behavior Tree） |
| :--- | :--- | :--- |
| **适用场景** | 状态数量少、流转逻辑严谨的场景（如裁判盒比赛状态转移） | 任务行为繁多、需要频繁组合与复用的场景（如进攻防守策略） |
| **局限性** | 状态增多时转移连线指数级膨胀，维护成本高 | 缺乏显式时钟控制，对严格毫秒级时序敏感度低 |
| **调试支持** | 打印当前状态名称与触发事件 | 支持状态树可视化，直观查看节点返回状态 |

在系统架构中，底层通信与裁判状态管理使用有限状态机，高层战术决策使用行为树。

### 简化进攻行为树核心节点

| 节点类型 | 节点名称 | 逻辑作用 |
| :--- | :--- | :--- |
| 控制节点 | **Fallback** | 顺序执行子节点，只要有一个子节点返回成功，即整体返回成功 |
| 控制节点 | **Sequence（起身）** | 顺序执行全部子节点，全部返回成功时整体才返回成功 |
| 条件节点 | **IsFallen** | 检测 IMU 姿态角，判断机体是否发生倒地 |
| 动作节点 | **GetUp** | 触发执行倒地自主起身动作序列 |
| 控制节点 | **Sequence（进攻）** | 顺序调度寻球、接近球体与射门动作 |
| 动作节点 | **FindBall / ApproachBall / Kick** | 执行搜索球体、调整身位逼近与单腿踢球射门 |

编写行为树时注意：条件节点严禁引入修改外部状态的副作用；树结构深度避免过度嵌套；注意高层决策 tick 周期与底层控制频率的匹配。

## 4.7 粒子滤波与场地定位

足式里程计能够推算短时位移但误差会持续累积；视觉观测能提供场地标线等绝对位置特征，但由于草皮对称性可能引起镜像歧义。蒙特卡洛粒子滤波（MCL）通过在状态空间中维护一组候选位姿粒子，融合运动预测与视觉特征，完成全局位姿估计。

### 核心解算流程

1. **粒子状态初始化**：在球场范围内生成大量随机粒子，每个粒子携带一个候选空间坐标与朝向角度 $(x, y, \theta)$。
2. **运动学预测更新**：读取足式里程计位移增量，将运动变化叠加到所有粒子上，并加入运动高斯噪声。
3. **视觉特征观测更新**：将当前帧检测到的白线、圆心与球门位置，与各粒子理论视角下的地图特征进行比对，根据匹配度计算并赋予粒子权重。
4. **重要性重采样**：按照权重分布对粒子群进行重采样，复制高置信度粒子，淘汰低权重粒子。
5. **输出全局位姿**：聚类计算粒子群的重心与均值，输出当前机体在地图坐标系中的全局位姿及协方差。

| 调优参数 | 典型范围 | 调整影响 |
| :--- | :--- | :--- |
| **粒子数量** | 500–2000 个 | 粒子过多增加机载 CPU 负担；粒子过少易导致滤波发散 |
| **运动噪声参数** | 根据打滑实测标定 | 设置过小会导致跟丢真实轨迹；设置过大会使粒子群过度分散 |
| **观测噪声参数** | 根据视觉标定误差设定 | 设置过小会导致过度信任单次观测；设置过大会忽略有效观测 |
| **重采样阈值** | 有效粒子数降至总数一半时触发 | 重采样过频会丢失多样性，重采样过慢会导致收敛迟滞 |

### 常见定位问题

- **镜像歧义解**：球场关于中线几何对称，若初始粒子分散可能收敛至对称半场。引入指南针航向角约束或根据球门颜色特征区分半场。
- **视觉特征缺失**：机器人处于开阔中场且被其他机器人遮挡时缺少标线特征。此时依靠里程计运动学进行短时航位推算，避免强行重采样。
- **位姿跟丢恢复**：遇到外部猛烈碰撞导致定位完全失效时，触发全局重定位逻辑，重新全场撒点寻找几何匹配。

## 4.8 深度强化学习的适用范围

本节为进阶选读内容，梳理双足运动控制论文中常见的基础概念：

| 核心概念 | 说明 |
| :--- | :--- |
| **贝尔曼方程** | 当前状态价值等于即时回报加上经过折减的未来期望价值 |
| **时序差分（TD）** | 基于后续时间步的估计值直接更新当前步价值估计，无需等待回合结束 |
| **蒙特卡洛方法** | 完整运行至回合终局，依据实际累计总回报更新策略参数 |
| **策略网络（Policy Network）** | 以前端观测为输入，直接输出各关节目标动作的神经网络 |
| **Actor-Critic 架构** | 由 Actor 网络负责输出动作，Critic 网络负责对状态动作进行打分评估 |
| **PPO 算法** | 限制每次策略更新的步长幅度，防止训练发散，在双足步态控制中应用广泛 |

### 部署到真机前的限制与评估

- **真机试错成本高昂**：双足机器人频繁摔倒将损坏减速器齿轮与碳纤维结构件，策略训练与筛选必须在 Isaac Gym 或 MuJoCo 等物理仿真引擎中完成。
- **仿真与现实差距（Sim2Real Gap）**：仿真接触模型与实际人工草皮摩擦力、电机驱动器响应延迟存在差异。训练时必须引入域随机化（Domain Randomization）对质量分布、摩擦系数与通信延迟施加扰动。
- **黑盒策略可解释性**：端到端神经网络难以直观分析特定动作选择的具体原因，现场调试与紧急修复难度较大。通常建议结合残差控制或基于经典控制框架进行策略融合。
