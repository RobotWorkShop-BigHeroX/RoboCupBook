## 4.1 可以暂缓深入的内容

之所以建议新人在入队初期暂缓钻研以下方向，是因为在尚未建立整机数据流全貌之前，过早陷入孤立的底层细节极易引发严重的挫败感，迫使学习进度停滞在细枝末节上：

- **DDS 底层报文协议细节**：初期只需掌握节点自动发现、话题发布订阅与服务调用的基本使用，只有在遭遇局域网内广播风暴或跨网段断连等网络疑难杂症时，才需要抓包分析 RTPS 报文头。
- **Executor 调度器的内部源码**：先掌握单线程与多线程执行器的调度差异，明确耗时计算会阻塞同一执行器内的其他回调即可，无需通读其源码调度循环。
- **C++ 高阶模板元编程**：现有工程中大量运用了模板封装，阅读时能看懂接口调用形式即可，避免在语法技巧上耗费过多时间。
- **强化学习算法收敛性证明**：重点理解训练流程、动作空间与观测空间的定义方式，数学证明不影响工程调试。
- **复杂文档排版技巧**：集中精力于技术事实与工程逻辑的准确表达，排版工具按需查阅即可。

## 4.2 Git：建立严格的工程协作习惯

在多人协同开发大型机器人工程时，Git 不仅是版本备份工具，更是维护代码稳定性的第一道防线：

| 任务场景                   | 推荐命令                                        | 操作目的与注意事项                                                             |
| :------------------------- | :---------------------------------------------- | :----------------------------------------------------------------------------- |
| **查看工作区变动**   | `git status`、`git diff`                    | 提交前逐行比对修改，避免误将本地临时测试日志或中间产物混入暂存区               |
| **精细化暂存**       | `git add -p`                                  | 交互式逐块审查改动，杜绝将无关修改强行打包                                     |
| **原子化提交**       | `git commit -m "fix: 修正踝关节俯仰零位偏置"` | 保持单次提交的语义原子性，便于后续故障二分回溯（`git bisect`）               |
| **同步远程分支提交** | `git pull --rebase`                           | 维持清晰线性的提交历史，避免产生大量无意义的分支合并节点                       |
| **开辟特性分支**     | `git switch -c feat/ball-tracking`            | 隔离新功能开发，维持主分支始终处于可编译、可测试状态                           |
| **丢弃工作区修改**   | `git restore <file>`                          | 放弃未提交的临时改动；若需撤销已推送提交，必须使用 `git revert` 生成逆向提交 |
| **更新私有子模块**   | `git submodule update --init --recursive`     | 使底层依赖库与私有技术手册同步至指定版本校验码                                 |

团队协作中必须严格恪守三条纪律：

1. **严禁对公共受保护分支执行强行推送（`force push`）**：强行覆盖远程分支将直接破坏其他协作者的本地提交基底，导致灾难性的代码丢失与繁琐的重组代价。
2. **坚持单一职责原则**：严禁在一个提交中同时混合“功能开发”与“全工程代码格式化”。这会导致代码审查完全无法聚焦，在遭遇缺陷需要回溯时，也会直接剥夺原子化撤销的可能性。
3. **提交 PR 前必须在本地通过全套构建与静态检查**：CI 自动化工作流仅作为辅助防线，开发者必须对自身推送代码的本地编译与基本功能负责。

## 4.3 ROS 2 的常用机制与适用场景

ROS 2 是机器人软件的神经系统。各个核心机制的设计直接对应着特定的工程解题需求：

| 核心机制                         | 解决的工程问题                             | 常见调试与故障场景                                        |
| :------------------------------- | :----------------------------------------- | :-------------------------------------------------------- |
| **DDS / RTPS**             | 去中心化节点自动发现与高吞吐网络传输       | 局域网内某台机器人重启后，排查节点是否能自动恢复拓扑连接  |
| **节点与通信模型**         | 模块独立运行，通过话题、服务与动作交换数据 | 梳理系统架构与数据调用关系，划分模块职责边界              |
| **QoS 服务质量策略**       | 规定消息可靠性、队列缓冲深度与保活要求     | 解决相机画面延迟过高、控制指令堆积或比赛状态偶发丢包      |
| **Executor 执行器**        | 调度回调函数并发线程与优先级               | 解决控制周期抖动、高频通信丢帧与多回调死锁问题            |
| **Lifecycle 生命周期**     | 提供明确的节点状态机（未配置/激活/失活）   | 比赛上场前顺序自检与停机安全保护                          |
| **Node Composition**       | 支持多节点在同一进程中运行，实现零拷贝通信 | 解决高分辨率高帧率图像在进程间拷贝占用过高 CPU 资源的问题 |
| **TF2 坐标变换系统**       | 维护机器人机体、传感器与球场的空间树形转换 | 将图像中识别到的目标映射为球场绝对坐标                    |
| **rosbag2 数据录制与回放** | 完整记录现场传感器与话题通信时序数据       | 赛后离线回放现场数据复现偶发故障                          |

### QoS 配置策略的选择依据

- **视频图像流**：相机传输 1080P/720P 原始帧时数据通量极高。必须采用 `BEST_EFFORT`（尽力而为）传输模式并将队列深度设为 1。之所以这样设置，是因为在图像处理链路中，下一帧新图像永远比上一帧更具时效价值；如果误配置为 `RELIABLE`（可靠传输），一旦出现单帧网络丢包，通信中间件将不断发起重传重试，由此导致历史画面帧在缓冲区发生严重堆积，造成机器人看到的视野产生数秒的时延滞后。
- **裁判盒与状态机指令**：必须采用 `RELIABLE` 模式。比赛状态切换指令低频但极为致命，漏收一次便会导致机器人无法按时开球或违规受罚，绝不允许丢失。
- **高频 IMU 姿态反馈**：通常采用 `BEST_EFFORT` 传输且队列设为 1，使运动控制回调函数获取到的数值始终保持当前最新。

## 4.5 视觉检测：YOLO11、YOLO26 与工程流水线

视觉感知的核心目标是从高频图像像素中稳定提取目标空间特征。

### 1. 模型选型与定位

- **YOLO11（队内主力与最稳定基准）**：作为当前工程实战的主选方案。其算法稳定性、推理吞吐与模型轻量化兼顾良好，拥有极其完善的 ONNX 与 TensorRT 工具链支持。在机载 i7-1355U / Orin 平台上能够稳定维持 30 FPS 以上的推理频率，检测抖动与远距离漏检率表现均衡，是新成员首选跑通的标杆模型。
- **YOLO26（前沿探索与可选研究）**：最新一代检测架构，引入了更精细的多尺度注意力融合与端到端无 NMS 设计。本书不做全队强制要求，鼓励对视觉前沿感兴趣的成员进行实验对比，评估其在强逆光、草皮大面积反光以及远距离球门立柱等极限场景下的特征表征能力。

### 2. 用途与使用流程（怎么用）

```mermaid
graph LR
    A["现场视频采集与抽帧"] --> B["标注足球与球门立柱"]
    B --> C["数据增强与色温扰动"]
    C --> D["模型训练与 mAP 评估"]
    D --> E["导出 ONNX / TensorRT"]
    E --> F["ROS 2 推理节点集成"]
    F --> G["逆透视投影计算相对坐标"]
```

1. **样本采集与标注**：在人工草皮现场采集多时间段图像，覆盖强反光、逆光与阴影场景。使用标准工具对黑白足球、球门立柱底座与白线交点进行外接框标注。
2. **离线训练与优化**：引入高斯噪声、色彩饱和度抖动与随机仿射变换进行数据增强；训练收敛后评估模型在验证集上的 mAP 指标。
3. **引擎导出与端侧加速**：将 PyTorch 模型权重导出为标准 ONNX 格式，随后利用 TensorRT 执行 FP16 精度量化生成机载推理引擎。
4. **机载 ROS 2 推理节点集成**：节点订阅相机图像话题，执行 TensorRT 前向推理并将检测框坐标发布至 `/perception/detected_objects` 话题；随后几何解析模块结合相机内参矩阵与外参标定数据，通过逆透视投影（IPM）解算目标在机体坐标系下的三维相对空间坐标。

## 4.6 行为树：任务规划与状态解耦

战术策略层通常采用行为树（BehaviorTree）替代复杂的嵌套状态机：

| 节点类型           | 典型节点                                 | 调度机制与工程作用                                                              |
| :----------------- | :--------------------------------------- | :------------------------------------------------------------------------------ |
| **控制节点** | **Fallback**                       | 顺序尝试执行各子节点，只要有一个子节点返回 SUCCESS 便立刻返回，用于处理容错兜底 |
| **控制节点** | **Sequence（起身）**               | 仅当所有子节点均返回 SUCCESS 时才返回成功，用于执行倒地起身固定序列             |
| **条件节点** | **IsFallen**                       | 仅读取 IMU 姿态判定机体是否倒地，只读查询，严禁引入改变外部状态的副作用         |
| **动作节点** | **GetUp**                          | 触发底层运动控制器执行起身轨迹                                                  |
| **控制节点** | **Sequence（进攻）**               | 顺序调度寻球、接近球体与射门动作                                                |
| **动作节点** | **FindBall / ApproachBall / Kick** | 执行旋转寻球、调整身位逼近与单腿踢球动作                                        |

编写行为树时必须遵守两项核心准则：

- **条件节点绝对严禁引入副作用**：条件节点在行为树每个 tick 周期都会被高频轮询。如果开发者在检查“是否看到足球”的同时顺手修改了全局目标变量，当行为树发生逻辑回溯时，将引发不可预测的循环震荡。
- **严格匹配决策 tick 周期与底层控制频率**：行为树通常以 10 至 20 Hz 的低频运行，而底层运动控制运行在 200 Hz。行为树下发的瞬态速度跳变必须经过平滑加速度插值器过滤，避免阶跃速度指令直接导致电机过流或机体失稳。

## 4.7 粒子滤波与 TF2 全局定位架构

赛事规则严厉禁止使用任何激光雷达，而深度相机在室外强烈太阳光与场馆大功率射灯下极易产生大面积点云噪点且受到严格检录审查。这迫使双足机器人必须完全依赖可见光单目/双目相机配合足式里程计实现全场定位。

蒙特卡洛粒子滤波（MCL）结合 ROS 2 的 TF2 坐标变换树，构成了全自主定位的核心实现链路：

### 1. TF2 坐标树的分层组织

```mermaid
graph TD
    map["map (场地绝对坐标系，原点位于球场中心)"] -->|动态校正变换由粒子滤波发布| odom["odom (里程计连续坐标系)"]
    odom -->|高频运动学积分连续推算| base_link["base_link (机体几何中心)"]
    base_link -->|静态机械安装参数标定| camera_link["camera_link (相机光学中心)"]
```

- **`odom -> base_link`**：由足式里程计根据电机编码器与 IMU 角度以 100–200 Hz 高频推算发布。该变换保持严格连续、绝对无阶跃跳变，供底层行走控制器做高频闭环，但其位置会随行走打滑不断产生漂移。
- **`map -> odom`**：由粒子滤波算法以 10–30 Hz 低频发布。粒子滤波保持 `base_link` 连续位姿不变，将累积漂移计算为 `map -> odom` 的相对偏差补偿，使得最终的 `map -> base_link` 能够平稳收敛到球场绝对真实坐标。

### 2. 粒子滤波计算闭环步骤

1. **初始撒点**：在球场范围内生成数百至上千个候选粒子，每个粒子表征机器人在 `map` 坐标系下的候选位姿 $(x, y, \theta)$。
2. **运动学预测（Prediction）**：读取上一周期至当前周期的里程计位移增量，将机体平移与旋转增量叠加至每一个粒子，并加入高斯扰动以模拟足底打滑。
3. **视觉观测比对（Observation Update）**：相机在 `camera_link` 坐标系下检测到白线交点、中圈弧线与球门立柱，经静态外参转换到 `base_link`；随后根据各候选粒子的假设位姿，计算这些特征在 `map` 场地地图中的预期投影位置。观测特征与实际地图特征吻合度越高，赋予该粒子的权重得分越高。
4. **重采样筛选（Resampling）**：淘汰得分过低的无效粒子，依据权重比例在高分粒子周围重新复制生成粒子群，迫使粒子迅速向真实坐标聚集。
5. **发布坐标更新**：计算高分粒子群的统计重心，求得当前机器人在 `map` 下的最佳估计位姿，逆向推导并发布当前的 `map -> odom` 坐标变换。

| 调参项目 | 典型范围 | 调整影响与权衡取舍 |
| :--- | :--- | :--- |
| **粒子数量** | 500–2000 个 | 粒子过多拖慢机载工控机计算；粒子过少容易跟丢位置 |
| **运动噪声参数** | 根据实测打滑程度标定 | 设置过小会导致跟丢真实轨迹；设置过大会让粒子散得太开 |
| **观测噪声参数** | 根据相机标定精度设定 | 设置过小会过度轻信单次画面抖动；设置过大会忽略看到的有效标线 |
| **重采样阈值** | 有效粒子降到总数一半时触发 | 重采样太频繁会丧失寻找备选位置的能力，太慢会导致坐标更新迟钝 |

### 常见定位问题与处理方法

- **半场认反**：足球场关于中线几何完全对称，两端白线和球门完全一致。如果机体跌倒爬起后初始航向出现大偏差，粒子群可能聚拢在对称的镜像位置。必须结合机载磁力计航向角，或在开赛前根据裁判盒广播的半场防守方向硬性锁定初始朝向。
- **标线短暂遮挡**：机器人身处开阔中场或视线被队友遮挡时，视野中缺乏特征。此时保持由里程计维持推算，暂时停止粒子重采样，避免在缺乏观测事实时强行收拢粒子。
- **碰撞后重新定位**：遭受猛烈冲撞导致当前位置彻底跟丢时，触发全场全局重新撒点，控制机身旋转扫描四周场地白线加速定位收敛。

## 4.8 深度强化学习的适用范围

本节为进阶选读内容，不做硬性技术考核，供有志于双足运动控制前沿研究的成员建立技术图谱：

| 核心算法与概念 | 数学物理内涵 | 在双足控制中的具体角色 |
| :--- | :--- | :--- |
| **贝尔曼优化（Bellman Optimization）** | 基于动态规划子结构性质，通过价值迭代逐步逼近系统目标控制策略 | 强化学习决策收敛的理论基石 |
| **贝尔曼最优方程（BOE）** | $V^*(s) = \max_a \sum_{s'} P(s'|s,a)[R(s,a,s') + \gamma V^*(s')]$ | 建立动态规划自洽极值边界 |
| **时序差分（TD）** | 基于当前即时奖励与后续状态价值估计执行单步或多步更新 | 避免等待完整比赛回合结束，极大提升足底冲击交替时的样本利用效率 |
| **蒙特卡洛方法（Monte Carlo）** | 通过大量完整对抗轨迹的累计采样平均值估算价值函数 | 不依赖环境转移概率马尔可夫先验，但方差偏大 |
| **策略网络（Policy Network）** | 将机体姿态、角速度与足底接触状态映射为电机目标角度的神经网络 | 端到端生成高动态抗扰动步态轨迹 |
| **Actor-Critic 架构** | Actor 网络负责生成控制动作，Critic 网络负责对当前状态价值打分评估 | 降低策略梯度估计方差，促使训练平稳收敛 |
| **Q-learning** | 经典的离线策略值迭代算法，通过更新动作价值函数寻找离散动作目标解 | 适用于高层进攻防守离散决策选项的离线优化 |
| **DDPG 算法** | 结合 Actor-Critic 思想与 Q 学习机制，直接输出高维连续动作空间力矩 | 探索双足机器人下肢连续关节力矩直接驱动控制 |
| **PPO 算法** | 通过概率比率剪切机制严格限制每次策略更新步长，防止策略剧烈震荡 | 当前四足与双足机器人步态训练中应用最为广泛、鲁棒性最高的代表性算法 |

### 部署到真机前的物理制约与风险评估

- **真机跌落与机械磨损代价**：双足机器人在真机上直接试错成本极高。每次高动态跌落都会对高减速比行星齿轮箱与轴承施加剧烈剪切载荷，因此策略训练与初步筛选必须在 Isaac Gym 或 MuJoCo 等高并发物理仿真引擎中完成。
- **仿真与现实差距（Sim2Real Gap）**：仿真接触模型与实际人工草皮摩擦力、电机驱动器响应延迟存在差异。训练时必须引入域随机化（Domain Randomization）对质量分布、摩擦系数与通信延迟施加扰动。
- **黑盒策略可解释性**：端到端神经网络难以直观分析特定动作选择的具体原因，现场调试与紧急修复难度较大。通常建议结合残差控制或基于经典控制框架进行策略融合。
