使用这些命令时，还需要遵守三条协作约定：

\begin{enumerate}[leftmargin=*]
    \item \textbf{不要对公共分支执行 force push。} 这可能覆盖其他人的提交，恢复起来也更困难。
    \item \textbf{一个提交尽量只处理一类改动。} 如果修复缺陷时同时大规模格式化，后续审查和回滚都会更困难。
    \item \textbf{提交 PR 前先在本地验证。} 自动化检查可以补充本地测试，但不应替代开发者自己的基本验证。
\end{enumerate}

\noindent 可以新建一个练习仓库，配置 GitHub Actions，在推送代码时自动运行 lint 检查。完成一次从提交到自动检查的流程后，再阅读团队项目中的 CI 配置会更容易。

\noindent\textbf{例如，QoS 配置会影响图像延迟。} 假设相机话题使用可靠传输，队列深度设为 10。当消费者处理速度低于相机帧率时，消息可能逐渐积压，控制回路读到的便不再是最新画面。机器人根据旧观测移动时，问题表面上可能像是控制参数不合适，实际原因却是数据延迟。

对于强调实时性的图像流，常见做法是使用尽力传输并将队列深度设为 1，以减少旧帧积压；但具体配置仍应根据消费者行为、通信环境和中间件实现测试确认。裁判盒状态通常更重视可靠接收，程序也应考虑丢包后的状态恢复，而不能只依赖单个数据包。

\noindent\textbf{先理解一条基本的坐标变换链。} 相机检测到的球的位置最初位于相机坐标系中；若要在场地坐标系下规划动作，就需要依次应用相机到机体、机体到里程计、里程计到地图的变换。通常，机械模型和里程计提供前两段关系，定位模块发布 \texttt{map} \(\rightarrow\) \texttt{odom} 变换。第 4.7 节会进一步说明这部分内容。

\noindent\textbf{将这些机制放到一条数据链中理解。} 例如：

相机 30 Hz 出一帧 \(\rightarrow\) 视觉节点缩放到 640\(\times\)640，跑一次推理 \(\rightarrow\) 输出「球在哪、球门柱在哪」\(\rightarrow\) 定位节点拿观测和里程计更新粒子 \(\rightarrow\) 决策节点 10 Hz tick 一次，输出目标速度 \(\rightarrow\) 运动控制 200 Hz 把速度变成关节指令。

链路中的每一段都会引入处理和通信延迟，端到端延迟需要通过时间戳或性能分析工具测量。遇到机器人反应迟缓时，应先测量各模块的耗时，再决定优化方向，而不是直接调整控制参数。

将条件判断与动作节点分开，有助于阅读树的执行顺序，也便于定位失败发生在哪个条件或动作上。

实现时需要特别注意以下问题：

\begin{itemize}[leftmargin=*]
    \item \textbf{条件节点有副作用。} 检查「是否看到球」的时候顺手改了状态，树的行为就不可预测。
    \item \textbf{树太深。} 层级过多会增加理解和调试成本；是否拆分应结合节点复用情况与实际排查难度决定。
    \item \textbf{决策频率和 tick 频率不一致。} 树每 50 ms tick 一次，但底层控制 200 Hz，中间要加一层平滑。
\end{itemize}

\subsection{粒子滤波与场地定位}

里程计能够估计机器人相对移动了多远，但误差会逐步累积；视觉可以提供场地标记等绝对位置线索，却可能因为遮挡或场地结构对称而产生歧义。粒子滤波通过维护多个候选位姿，并结合运动预测和视觉观测，估计机器人当前的位置与朝向。

每个粒子表示一个候选位姿，权重用于表示该位姿与当前观测的一致程度。

\begin{enumerate}[leftmargin=*]
    \item \textbf{初始化候选位姿。} 在场地范围内生成若干候选位置与朝向，每个粒子代表一种可能的机器人位姿。
    \item \textbf{运动预测。} 根据里程计增量更新每个粒子的位置与朝向，并将运动估计中的不确定性纳入模型。
    \item \textbf{观测更新。} 根据当前视觉特征与各粒子预测观测之间的一致程度更新权重。
    \item \textbf{重采样。} 按粒子权重重新抽样，使高概率区域得到更多代表，同时保留足够的多样性以应对定位不确定性。
    \item \textbf{输出位姿估计。} 根据粒子分布计算位置与朝向估计，并按系统约定发布定位结果及相关坐标变换。
\end{enumerate}

\noindent\textbf{与 TF 的关系：} 定位模块通常发布 \texttt{map} \(\rightarrow\) \texttt{odom}；里程计提供 \texttt{odom} \(\rightarrow\) \texttt{base}；机器人描述文件（URDF）与关节状态用于确定 \texttt{base} \(\rightarrow\) \texttt{camera}。三段变换必须使用一致的坐标约定，否则即使机器人位姿看似合理，球的位置也可能出现明显偏差。

\noindent\textbf{常见问题：}

\begin{itemize}[leftmargin=*]
    \item \textbf{镜像解。} 中圈两边标线对称，粒子可能收敛到对面的位置。加朝向先验，或者用球门的不对称性区分。
    \item \textbf{特征太少。} 如果视野中缺少可识别的场地标记，应结合运动模型维持短时估计，并避免在观测不足时过度依赖重采样。
    \item \textbf{跟丢之后不恢复。} 要有一个「全局重定位」的兜底：粒子散满全场，等下一次观测把它拉回来。
\end{itemize}

\noindent\textbf{使用前需要评估的限制：}

\begin{itemize}[leftmargin=*]
    \item 数据获取成本高。真机上的反复失败测试成本高且存在设备风险，通常需要先在仿真环境中训练和筛选策略。
    \item 仿真与真机存在较大差异。接触模型、执行器延迟和地面摩擦等因素都可能影响策略迁移效果。
    \item 系统需要较强的可解释性。若策略难以说明某次动作选择的原因，现场故障分析和针对性修正会更困难。
\end{itemize}

\noindent 如果决定尝试，可以先在 Zlab\_Gym 或 Isaac 中验证基础任务，再逐步加入域随机化，并评估是否适合通过残差控制与现有步态结合。部署到真机前，应完成仿真测试、保护机制检查和受控条件下的渐进验证。\advice
